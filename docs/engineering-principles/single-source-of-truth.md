# 唯一の事実源（Single Source of Truth）

すべての宣言的事実は、唯一の権威ある所有者（Authoritative Owner）を持たなければなりません。これには、スキーマ定義、依存関係のバージョン、インフラ定義、デプロイ設定などが含まれます。

これらの事実をテストコードやヘルパースクリプト内に複製してハードコードすると、「第2の権威」が生まれます。複製されたデータは時間の経過とともに元の定義と乖離（ドリフト）し、1つの変更に対して複数箇所の同期編集を強いられるようになります。ミスを防ぐために追加したチェックが、かえってミスを生む温床となってしまいます。

## 設計ルール

検証手法を選択する前に、まず**唯一の事実源（Source of Truth）**を決定します。他のコンポーネントはその事実源を直接読み込むか、その実行結果を観測すべきであり、期待値のリストを並行して再定義してはなりません。

* **派生成果物（Derived Artifacts）**: 機械的に自動生成され、いつでも破棄・再生成できるものであれば複製であっても安全です。
* **手動管理のコピー**: 手動で保守されているコピーは派生物ではなく、「競合する別の権威」です。

## 所有権には「解釈」も含まれる

単一の所有権は、保存された値だけでなく、その「意味論（Semantics）」にも適用されます。フォーマットやプロトコルを定義したサブシステムこそが、その構文、意味、ライフサイクルを最も深く理解しています。したがって、権威ある事実源の解釈は、その所有者が提供するネイティブな実行・検証機構に委ねるべきです。

自前のスクリプトでそれらの解釈ルールを再実装すると、たとえ元の事実源を読み込んでいたとしても、第2の意味論的権威を作り出してしまいます。独自のインタープリタは仕様変更やエッジケースに追従しきれず、겉보기には正しく見えながら徐々に乖離していく原因になります。

検証を検討する際は、以下の優先順位に従います。

1. 所有サブシステムの通常の実行パス
2. そのサブシステムが提供するネイティブな検証・計画コマンド
3. アプリケーション境界における振る舞いテスト
4. 独自チェッカー（上記の方法では表現できないプロジェクト固有の知識を追加する場合にのみ限定）

## 設計時に問いかけるべき質問

* この事実を所有しているファイルやサブシステムはどれか？
* 将来の変更において、同じ事実を2箇所で編集する必要が生じないか？
* 利用側のコンポーネントは、権威ある定義を直接参照・適用できるか？
* 所有サブシステム自身が、自らの定義を解釈・強制しているか？
* 自動生成された成果物が、リポジトリの元ソースと混同されていないか？
