# あるべき姿を宣言し、自律的に差分を収束させる（Declarative and Reconciliation）

目標とする**「あるべき最終状態（望ましい姿）」をデータとして定義し、現実との差分をシステム自身に継続して埋めさせること**を設計の基本姿勢とします。

そこに到達するための逐次的な手順を1ステップずつ手作業で指示するのではなく、また「一度スクリプトを実行して祈る」のでもなく、目指すべきゴールを宣言し、そこへ向かって現実を収束させ続ける仕組みを築きます。

## 手続き的な指示が抱える脆さ

「まず A を作り、次に B を設定し、その後に C を実行する」といった一回限りの命令的な手順書（スクリプト）には、根本的な弱点があります。

途中で通信エラーが起きたり、誰かが途中で手動の変更を加えた場合、手順書の想定と現実のシステムの姿は静かに乖離（ズレ）していきます。その乖離は誰の目にも触れず放置され、ある日突然、深刻な障害となって表面化します。

一方、宣言的な仕組みにおいては、目指すべき状態（Desired State）をコードや設定として記録します。そして、**「宣言されたあるべき姿」と「現実の稼働状態」を継続的に見比べ、その差分を検出して自動的に解消し続ける調停の循環（リコンシリエーション）**を動かします。もし現場で予期せぬ揺らぎや一時的な不整合が生じても、次の調停サイクルが差分を検知し、自律的にあるべき姿へと現実を引き戻します。

## この原則がもたらす価値

* **自律的な自己修復（Self-healing）**: 一時的な障害、ネットワークの瞬断、あるいはコンポーネントの再起動が発生しても、システムは外からの手動介入を待つことなく、自律的にあるべき状態へ復帰します。
* **状態の乖離の可視化**: 現実が設計から外れている場合、その差分が即座に浮き彫りになります。
* **安全な変更と巻き戻し**: 変更は「望ましい状態の差分」として事前に評価でき、もし不具合が生じた場合でも、宣言を前の状態に戻すだけでシステム全体が安全に過去の姿へと自律的に収束していきます。

## アーキテクチャへの適用パターン

この宣言的調停の考え方は、システム設計において以下のような実践パターンとして具現化されます。

* **定期照合による状態の自己修復（アンチエントロピー）**: リアルタイム通信や非同期ストリーミングで取りこぼしたイベントを回復する仕組みを、障害時に人間が手動で実行する「命令的スクリプト」として作りません。直近の状態を定期的に巡回し、手元のデータ蓄積状況と外部情報源の現実を照合して未反映の差分を回収する「継続的な調停ループ」として定常稼働させます。
* **進行状態を自ら運ぶメッセージの連鎖（自律的分散処理）**: 巨大なバッチ処理を1つの統制プロセスから命令的に実行するのではなく、キューやメッセージ自身が「次に処理すべき位置や範囲」を携えて自律的に連鎖し、全体の完了という目標状態に向かって状態を持たずに（ステートレスに）収束させます。
