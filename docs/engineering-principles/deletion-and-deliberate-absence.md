# 削除と意図的な不在（Deletion and Deliberate Absence）

不要なチェック、重複したヘルパー、あるいは過剰なガードレールを削除することは、品質の低下ではなく、システムの信頼性と保証（Assurance）を向上させる重要な設計行為です。

権威が重複した仕組みや、たまたまその時存在した構造を過剰に守るチェックを削除することで、「1つの信頼できる定義」「それを保護する1つのメカニズム」「結果から得られる明確な証拠」という、責任の短い連鎖が確立されます。

## 「なぜ存在しないのか」を記録する

意図的に作らなかった仕組み（意図的な不在）は、背景を知らない将来の保守者にとって「考慮漏れ（抜け落ち）」に見えることがあります。十分なコンテキストが残されていないと、かつて意図して排除されたはずの冗長なヘルパーや不要な抽象化が、再びコードベースへ持ち込まれてしまいます。

設計文書や ADR は、以下の事項を永続化すべきです。

* 根底にある事実をどのコンポーネントが所有しているか
* どのメカニズムが本来の保証を提供しているか
* **どの並行した仕組みが「意図的に存在しない」のか**
* **なぜその不在が、より明快な境界とアーキテクチャを守るのか**

この記録は、一時的な実装差分の説明ではなく、将来にわたって維持すべき恒久的な責務境界の説明として記述されるべきです。

## 削除の規律

既存のガードレールやチェックを削除する際は、それが元々カバーしていた具体的なリスクを特定し、そのリスクが現在どこで適切に観測・抑止されているかを確認します。

削除が完了した後のリポジトリは、競合する複数の権威が排除され、問題が発生した際にどこを調査すべきかが誰の目にも一目瞭然な状態になっていなければなりません。
