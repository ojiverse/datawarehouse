# デフォルトでの不変性（Immutability by Default）

データや値は、デフォルトで**不変（Immutable）**でなければなりません。状態の変更は、既存のオブジェクトをインプレースで書き換えるのではなく、「現在の値から新しい値を生成する変換」として表現します。

## ミューテーション（破壊的変更）がもたらすリスク

破壊的変更（Mutation）は、データに「時間（タイミング）」の概念を持ち込みます。同一のオブジェクト参照が、アクセスされる瞬間によって異なる値を指し示すようになるため、正しさが「処理の実行順序」「隠れた参照エイリアス」「次に誰が書き込むか」という暗黙の前提に依存するようになります。これは時間的結合（Temporal Coupling）を生み、コードの局所的な論理推論を著しく困難にします。

不変性を保つことで、値は生成後に完全に安定します。呼び出し側は書き込みの競合を調整することなく安全にデータを共有でき、関数は与えられた入力のみに基づいて結果を決定論的に導出できます。また、一度検証を通過した値が後から勝手に改ざんされないため、型システムによる保護もはるかに強固になります。

## 設計ルール

ドメインモデル、関数の入出力、コレクション、および設定値は、すべて不変なデータとして設計を開始します。状態の変更は「値 A から値 B への明示的な変換」としてモデル化し、その遷移を責務を持つ境界において可視化します。

TypeScript 等の言語においては、`readonly` 修飾子や不変データ構造を活用し、プロパティやコレクションへの意図しない書き込みをコンパイル時に防止します。

## 例外としてのミューテーション

ステートフルな外部プラットフォームとの連携や、計測によって証明されたクリティカルな性能ボトルネックなど、特定の要件を満たすために破壊的変更が正当化される例外は存在します。しかし、単なる実装の簡便さは理由になりません。

ミューテーションが不可避な場合は、以下の規律を守ります。

* それを不可逆的に必要とする要件を特定する。
* 変更を最小限の所有コンポーネントと短い生存期間（ライフタイム）の内部に閉じ込める。
* その境界を越えてミュータブルな参照を外部へ漏洩させない。
* 許可された状態遷移と保護すべき不変条件を明示する。
* 設計から理由が自明でない場合は、[なぜミューテーションが必要なのか（Why）](comments-explain-why.md) をコメントに記録する。

不変性は特別な許可を必要としませんが、可変性（Mutability）はそれを導入する側に厳格な説明責任が課されます。
