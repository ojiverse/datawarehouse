# 現在の確実性のレベルで設計する（Design at the Current Level of Certainty）

設計は、**すでに確定している既知の事実に対しては厳格（Strict）であり、まだ判明していない未知の事柄に対しては寛容（Permissive）**でなければなりません。設計の目的は、システムの将来の姿を先回りしてすべて予測し尽くすことではありません。現時点で正当化される意味と制約を確実に保護しながら、まだ具体的になっていない将来要件のために意図して「余白」を残すことです。

これは、新しいデータソースやドメインを追加する初期段階において極めて重要です。分類体系、派生状態、検索インデックス、キャッシュ構造、ライフサイクルモデルなど、将来ありそうな概念を想像することは容易です。しかし、「ありそうだ」というもっともらしさは、それ自体が要件であることを意味しません。それらを早期に設計へ焼き込んでしまうと、「将来に対する単なる期待」が「現在に対する硬直した制約」へとすり替わってしまいます。

したがって、真に問うべきは「これは将来どうなり得るか？」ではなく、**「いま判明している事実に照らして、何を失ったり矛盾させたりしてはならないか？」**です。

## 生き残るべき事実から始める

システムが永続化すべき振る舞いや意味から考え始め、それを保護する最小限の不変条件を導出します。たとえば、データソースがある時間的意味を持つ事実を報告しているのであれば、長期的に守るべき設計上の関心事は「その意味論が解釈の過程で失われないこと」です。特定のテーブルレイアウトや抽象型を直ちに決定する必要はありません。

意味的な差異は、その表現形式（ストレージ構造や型）よりもはるかに安定しています。2つのデータが等価として扱えないことが明らかであっても、それらを別個のテーブルに分けるべきか、異なるバリデーションルールで扱うべきかは、要件が深まるまで判断を保留できます。まず意味の区別を確定させ、表現形式の決定は要件がそれを正当化するまで待ちます。

所有権についても同様です。プロバイダ固有の生データがドメインの正（Truth）を汚染してはならないのであれば、生データとドメイン解釈の間に明確な境界を引きます。その境界が求める以上の汎用フレームワークを直ちに発明してはなりません。優れた抽象化とは「複数の実例によって証明された共通の不変条件」を表現するものであり、将来のユースケース間の表面的な類似性だけでは抽象化の根拠になりません。

## 不確実性を設計情報として扱う

設計中の未解決の疑問は、必ずしも設計の不備を意味しません。多くの場合、それは「システムが責任を持って決定を下すための十分な要件をまだ持ち合わせていない」という証拠です。

既知の不変条件を守るために今すぐ決定する必要がない事柄は、後の段階で情報を失わずに、かつ既存の契約を壊さずに決定できるのであれば、**意図して決定を未確定のまま保留（Open）**にします。ストレージレイアウト、保持期間、リビジョン管理戦略、派生モデルなどは、初期設計においてこのカテゴリーに分類される典型例です。

これは曖昧な契約を放置することを意味しません。既知の不変条件は型やドメイン定義を用いて極めて精密に表現します。重要なのは「精度」と「推測」の区別です。**確認済みの意味を破ることを困難にする一方で、未確認の分類体系を変更困難にしてはなりません。**

判断は次のように扱います。

- **確認済みの意味や制約**: 明示的かつ恒久的に固定する。
- **もっともらしい将来要件**: 受け入れる余白を残しておく。
- **代替可能な実装の選択**: ドメインの契約の外側に隔離しておく。

決定の永続性が高ければ高いほど、その決定を正当化するための証拠のハードルを上げなければなりません。局所的な実装詳細は安価に変更できますが、ドメイン概念や公開契約を後から巻き戻すことは極めて困難です。

## 議論の経過と設計の形状を混同しない

設計文書は、設計議論の経過を書き起こした議事録ではありません。設計者がどれほど多くの代替案を比較検討したとしても、初めてその文書を読む読者はその議論の歴史を共有しておらず、それを知る必要もありません。

「このドメインには、あえて〇〇という概念は存在しない」と書くためだけに、存在しない新しい概念を文書に登場させてはなりません。機能的な理由もなく読者のメンタルモデルを肥大化させてしまうためです。否定的な決定を記録すべきなのは、「要件や周辺アーキテクチャから見て、一般的な読者が当然その設計を採用すると推論してしまう場合」や、「不在そのものが重要な境界を保護している場合」に限られます。それ以外の却下されたアイデアは、文書から完全に省きます。

文書は、読者が理解するために必要な順序で整理されるべきであり、設計チームがそれを発見した順序で並べるべきではありません。各セクションは、次の決定を下すために必要な前提を確立するように構成します。読者は、過去の議論の紆余曲折を知ることなく、「なぜその境界が存在するのか」を論理的に導出できる必要があります。

## 早すぎる解釈よりも「情報の保存」を優先する

将来の要件が不確実な段階においては、背伸びしてリッチな解釈（過度な正規化）へコミットするよりも、**元の情報の意味と来歴（Provenance）を忠実に保存すること**の方がはるかに高い価値を持ちます。生き残った生データは後からいくらでも再解釈・再計算できますが、初期の安易な正規化によって削ぎ落とされた情報は二度と復元できないからです。

計算結果についても同様です。ある結果がドメインの事実から算出されたものであるならば、利便性のためだけにその計算結果を「第2の事実源」にしてはなりません。計算は、入力の本来の意味を消し去ったり、それと競合したりしてはならないという不変条件を守ります。

## 既知のことが守られたら設計を止める

設計は、**「すべての確定した要件に明確な不変条件と所有者が割り当てられ、利用側が小さく安定した契約に依存でき、未解決の疑問が情報の損失や矛盾を引き起こすことなく安全に保留されている状態」**に達した時点で、現在のフェーズとして十分に完成しています。

その地点を超えてさらに詳細を詰め込もうとすると、設計の品質を向上させるどころか、かえって低下させてしまいます。過剰な概念は、将来の作業者が遵守するか撤回しなければならない不要な語彙、依存関係、および暗黙の制約を生み出してしまうためです。

設計は、**要件 → 不変条件 → 権威ある所有者 → 最小限の安定した境界 → 観測可能な振る舞い**という短い連鎖で説明できる状態を目指します。

後に新しい要件が判明した際は、その新しい証拠に基づいてまったく同じ思考プロセスを繰り返します。初期の設計を「意地でも防衛しなければならない予言」として扱ってはなりません。真に耐久性のある設計とは、**「その時点で真実であったことに対して精密であり、それ以外のすべてを意図して再考可能な状態に残しておいた設計」**のことです。
