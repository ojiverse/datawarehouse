# 正規化データドメイン（Canonical Store）

本ディレクトリでは、Discord から収集した Observation（生の観測事実）を、長期間にわたり安定して検索・集計・分析可能な形式へ体系化した「Canonical Data」の意味論および設計原則を定義する。

## Canonical Store の役割と責務

Canonical Store は Observation Archive を代替するものではなく、明確な責務分担に基づく。

* **Observation Archive**: Discord から観測された事実を、解釈を挟まずに保存する生ログ。
* **Canonical Store**: 観測事実を読み解き、Discord DWH として整合的に解釈・構造化した分析用データモデル。

中核原則として、**Canonical Store は Observation Archive からいつでも完全に再構築（Rebuild）可能であること**を義務付ける。Canonical Store 側のデータ破損、変換ロジックの不具合、または大規模なスキーマ変更が発生した場合であっても、生データからの再計算・復元可能性を保証する。

## 対象エンティティのスコープ

初期フェーズにおいては、Discord の中核となる以下のエンティティにスコープを限定してモデルを策定する。

| エンティティ | 扱う関心事とデータ特性 |
| :--- | :--- |
| **Message** | 投稿内容、編集履歴、削除の追跡、添付ファイルや埋め込みのメタデータ |
| **Channel** | テキスト/ボイスチャンネルの作成、設定変更、トピック遷移、親カテゴリとの関係 |
| **Thread** | スレッドの作成、アーカイブ/アンアーカイブ状態、親チャンネルとの親子構造 |

※ Reaction、Member、Role、Voice State 等の拡張エンティティは、基本パイプラインの安定および具体的な分析要件の確定に伴い順次追加する。

## 履歴管理と最新状態（Current State）の導出

Canonical Store は、単一の更新可能レコード（上書き更新）を最終状態としない。

Message の編集や削除、HTTP スナップショットなど、同一エンティティに対して発生した複数の観測結果を時系列ログとして保持し、**クエリ実行時点または指定された過去時点における最新状態を「プロジェクション（投影）」として導出する設計**を採用する。
これにより、更新損失（Update anomaly）を防止するとともに、過去時点の状態を復元可能なタイムトラベル分析を実現する。

## 長期運用におけるスキーマ進化

5〜10年に及ぶ運用期間において、Discord API の仕様変更や DWH の集計要件拡張は定常的に発生する。

システムはスキーマ変更を定常的なライフサイクルとして扱い、旧形式データと新形式データの共存を保証するか、あるいは全 Observation を新変換規則でリプレイして Canonical Store を一新可能な再処理能力を中核機能として具備する。

## 分割予定の詳細設計

* **Canonical Data Model**: Message, Channel, Thread の正規化スキーマ定義
* **Message Model**: 本文、メンション、アタッチメント、編集/削除状態の表現規則
* **Channel & Thread Model**: チャンネル種別とスレッド階層構造の正規化
* **Historical State & Projection**: 履歴観測から最新状態を導出するプロジェクション規則
* **Schema Evolution**: 後方互換性を維持したカラム追加・型移行の運用モデル
