# ADR-0004: HTTP Backfill を定常的なアンチエントロピー機構とする方針

* **ステータス**: 承認（Accepted）
* **決定日**: 2026-09-20
* **対象領域**: ドメイン設計 / 運用アーキテクチャ

## コンテキストと課題

Discord のリアルタイムイベント受信（Gateway WebSocket）は、公衆網を介したストリーミング接続である。堅牢な接続管理を実施した場合であっても、以下の事象による潜在的な微小欠損（サイレントドロップ）のリスクが残存する。

1. **予期せぬ切断時の境界損失**: 切断検知から再接続までの間に、Discord 側のセッションバッファからイベントが溢れ出た場合。
2. **インフラ側の一時的障害**: キューへの投入失敗、ワーカーのクラッシュ、ダウンストリームの一時的遅延。
3. **長期運用に伴うエントロピー増大**: 長期運用のスパンにおいて、微小なイベント取りこぼしが蓄積し、全体のデータ整合性が静かに劣化するリスク。

通常、HTTP Backfill は「システムの初期導入時」や「大規模障害発生時」に手動起動する非常用ツールとして扱われやすい。しかし、人的検知と運用手順に依存する限り、潜在的なデータ欠損を防止することは困難である。

## 検討した選択肢

### 選択肢 1: Backfill を障害時・手動運用の非常用ツールとする
* **概要**: 平常時は Gateway のみでデータを受信し、切断アラート検知時や初期導入時にのみ Backfill を手動または自動起動する。
* **メリット**: Discord HTTP API のリクエスト消費を最小限に抑制可能。
* **デメリット**: Gateway が正常稼働に見える間に発生したサイレントな欠損を自己修復できず、データ欠落が長期放置されるリスクが高い。

### 選択肢 2: Backfill を定常的なアンチエントロピー機構として位置づける
* **概要**: Backfill パイプラインを定常機能とし、Cron スケジューラにより直近履歴を HTTP 経由で定期巡回・照合させる。

## 決定事項

**選択肢 2 を採用する。HTTP Backfill を定常的なアンチエントロピー（Anti-Entropy）機構としてアーキテクチャに組み込む。**

* **結果整合性（Eventual Consistency）の担保**: Gateway がメッセージを取り逃した場合であっても、バックグラウンドの定期巡回によって「最終的には必ずデータが回収される」整合性保証を確立する。
* **パイプラインの統一**: 初回ロード、障害リカバリ、および定常照合のすべてで同一の Backfill クローラーエンジンを利用し、実行頻度を高めて信頼性を担保する。
* **レート制限との調和**: 定常巡回は低優先度のバックグラウンドタスクとして実行し、Discord API のレート制限を圧迫しないインターバルで運用する。

## 結果とトレードオフ

### メリット
* **自己修復可能なデータ基盤**: 運用者が検知できない微小な通信障害やバグによる欠損が自動的に発見・補完され、データの信頼性が維持される。
* **運用の自動化**: 手動でのデータ照合や復旧運用の負担が削減される。

### デメリットと対応策
* **Discord API リクエスト数の増加**: 定期的な HTTP API 呼び出しにより、Bot のレート制限枠を一部消費する。
  * *対応*: 巡回対象を「全チャンネルの全履歴」ではなく「直近 N 日間にアクティビティが存在したチャンネル」に限定し、最小限のリクエスト数に抑制する。
