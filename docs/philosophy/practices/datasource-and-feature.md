# データソースと機能の設計ポリシー（Datasource and Feature Design Policy）

本ドキュメントは、新しいデータソースの取り込み、新規エンティティの追加、または派生プロジェクションを設計する際に遵守すべき設計方針を定めます。

中核となる基本原則は以下の通りです。

> **まずドメインの意味論と所有権を保護する。複数のデータソースや機能を扱う場合であっても、強引に単一の汎用レコードモデルへフラット化してはならない。**

---

## 1. プロバイダではなく「情報の意味論」から始める

外部プラットフォーム（プロバイダ）は、それ自体が自動的に 1 つのドメインになるわけではありません。データモデルを決定する前に、そのソースがどのような性質の情報をシステムにもたらすのかを分類します。

* **イベント証跡（Event Evidence）**: 特定の時点または時間区間に「何かが発生した」という事実。
* **現在の状態（State）**: ある時点で「何が真であるか」「何が保留されているか」という状態。
* **静的知識（Knowledge）**: イベントや最新状態そのものではないが、参照可能なコンテンツや定義。

1つのプロバイダが複数の意味論を提供することがあります（例: メッセージ投稿というイベント、現在のピン留めや権限という状態、チャンネル設定という知識）。それらを同じプロバイダから届くという理由だけで単一のデータ表現に無理やり押し込めてはなりません。

## 2. 構造化セマンティクスを忠実に保存する

プロバイダが安定した構造化フィールド（ID、タイムスタンプ、作成者、親子階層、ステータス等）を提供している場合、それらを安易に単なるテキストや非構造化メタデータへと削ぎ落としてはなりません。
構造化されたフィールドは、将来の集計、監査、フィルタリング、およびエンティティ照合において決定的な価値を持ちます。正規化されたテキスト表現が必要な場合であっても、それは導出された派生データであり、元の構造化データの代替ではありません。

## 3. 安定した識別性（Identity）と来歴（Provenance）の保持

後からデータを参照・再計算・照合できるようにするため、すべての正準レコードは以下を保持しなければなりません。

* システム内で一意かつ安定した論理 ID
* ソース名およびプロバイダ側のネイティブ ID
* 観測日時、取り込みバッチ ID、またはセッション/カーソル情報
* 削除や状態変更に関する証跡

表示用のテキストや可変な名前を識別子として使ってはなりません。

## 4. 履歴イベントと最新状態（Current State）の厳格な区別

「過去に発生したイベント履歴」と「現時点の最新状態」は、全く異なる目的を持ちます。
イベントログをただ集約しただけで最新状態を暗黙に決めつけるのではなく、プロジェクション（投影）のルールを明確にし、両者の意味を混同しない設計を維持します。

## 5. 検索インデックスや集計ビューは「使い捨て可能」とする

クエリ高速化のためのインデックス、集計キャッシュ、または全文検索テーブルは、すべて正準データ（Canonical Data）からいつでも再構築可能な「派生データ（Derived Data）」として扱います。
派生データが、ドメインの正（Truth）やデータ保持期間（Retention）に関する独自の権威を持ってはなりません。

## 6. 取り込みにおけるソース固有の不変条件を守る

あらゆる外部データソースを、最初から 1 つの「汎用取り込みフレームワーク」に押し込めてはなりません。
キューやスケジューラといったトランスポートインフラは共通化できますが、認証方式、レート制限への追従、ページネーション、セッション再開、リプレイ性といったプロトコル固有の不変条件は、各ソースのアダプタが責任を持って保護します。

## 設計チェックリスト

新しいデータソースや機能を追加する際は、以下の質問に明確に答えられることを確認します。

1. そのデータソースがもたらす意味論は何か（イベント、状態、知識、またはその組み合わせか）？
2. どのドメインが正準表現（Canonical Data）を所有し、どの表現が派生データか？
3. 保存すべきプロバイダ固有の識別子や構造化フィールドは何か？
4. すべてのレコードは安定した識別性と取得来歴（Provenance）を持っているか？
5. 過去の事実イベントと、現在の最新状態が明確に区別されているか？
6. 検索インデックスや派生ビューは、生データからいつでも再構築可能か？
7. レート制限、リトライ、ページネーションなどの外部制約は、ソースアダプタ内に適切に閉じ込められているか？
8. 複数の要件が真に不変条件を共有しているから抽象化するのか、単に見た目が似ているだけではないか？
