# データソースと機能の設計ポリシー（Datasource and Feature Design Policy）

本ドキュメントは、新規データソースの取り込み、新規エンティティの追加、および派生プロジェクションを設計する際に遵守すべき設計方針を定義する。

中核となる基本原則は以下の通りである。

> **まずドメインの意味論と所有権を保護する。複数のデータソースや機能を扱う場合であっても、強引に単一の汎用レコードモデルへフラット化してはならない。**

---

## 1. プロバイダではなく「情報の意味論」から始める

外部プラットフォーム（プロバイダ）は、それ自体が自動的に 1 つのドメインを構成するわけではない。データモデルを決定する前に、当該ソースがもたらす情報の意味論を以下のように分類する。

* **イベント証跡（Event Evidence）**: 特定の時点または時間区間に「何かが発生した」という事実。
* **現在の状態（State）**: ある時点で「何が真であるか」「何が保留されているか」という状態。
* **静的知識（Knowledge）**: イベントや最新状態そのものではないが、参照可能なコンテンツや定義。

単一プロバイダが複数の意味論を提供する場合がある（例: 操作履歴としてのイベント、権限設定としての状態、マスタ定義としての知識）。同一プロバイダ由来であることを理由に、これらを単一のデータ表現へ混同してはならない。

## 2. 構造化セマンティクスの完全保持

プロバイダが安定した構造化フィールド（ID、タイムスタンプ、作成者、親子階層、ステータス等）を提供している場合、これらを単なるテキストや非構造化メタデータへ削ぎ落としてはならない。

構造化フィールドは、将来の集計、監査、フィルタリング、およびエンティティ照合において決定的な価値を持つ。正規化されたテキスト表現が必要な場合であっても、それは導出された派生データであり、元の構造化データの代替ではない。

## 3. 安定した識別性（Identity）と来歴（Provenance）の保持

後からの参照・再計算・照合を保証するため、すべての正準レコードは以下を保持しなければならない。

* システム内で一意かつ安定した論理 ID
* ソース名およびプロバイダ側のネイティブ ID
* 観測日時、取り込みバッチ ID、またはセッション/カーソル情報
* 削除や状態変更に関する証跡

表示用のテキストや可変な名称を識別子として用いることを禁じる。

## 4. 履歴イベントと最新状態（Current State）の厳格な区別

「過去に発生したイベント履歴」と「現時点の最新状態」は異なる概念である。

イベントログの集約のみから暗黙に最新状態を決めつけるのではなく、プロジェクション（投影）規則を明示的に定義し、両者の意味論を混同しない設計を維持する。

## 5. 検索インデックスや集計ビューの再構築可能性

クエリ高速化のためのインデックス、集計キャッシュ、または全文検索テーブルは、すべて正準データ（Canonical Data）からいつでも再構築可能な「派生データ（Derived Data）」として扱う。

派生データが、ドメインの正（Truth）やデータ保持期間（Retention）に関する独自の権威を持ってはならない。

## 6. 取り込みにおけるソース固有不変条件の保護

外部データソースを、初期から単一の「汎用取り込みフレームワーク」へ統合してはならない。

通信やキューイングの実行基盤は共通化可能であるが、認証方式、レート制限追従、ページネーション、セッション再開、リプレイ性といったプロトコル固有の不変条件は、各ソースのアダプタがカプセル化して保護する。

---

## 設計時の評価項目

新規データソースや機能を追加する際は、以下の検証項目を満たすことを義務付ける。

1. 当該データソースの意味論（イベント、状態、知識）が特定されているか。
2. 正準表現（Canonical Data）を所有するドメインと、派生データ境界が分離されているか。
3. プロバイダ固有の識別子および構造化フィールドが保存されているか。
4. 全レコードが安定した識別性と取得来歴（Provenance）を保持しているか。
5. 過去のイベント事実と現在の最新状態が明確に区別されているか。
6. 検索インデックスや派生ビューが生データから完全再構築可能か。
7. レート制限、再試行、ページネーション等の外部制約がソースアダプタ内に閉じ込められているか。
8. 抽象化の根拠が真に共有された不変条件にあり、単なる表面的な類似性に基づいたものではないか。
