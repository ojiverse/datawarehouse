# 設計としての型システム（Types as Design）

型システムは、完成したコードに後から注釈（アノテーション）を付けるための道具ではありません。それは**設計を記述するための表現媒体**です。優れた設計は、実装ロジックを書き始める前に、ドメインの概念、有効な状態、許可された遷移、所有権、および境界の契約を型として表現します。

中核となる目的は、**設計に反するコードがそもそもコンパイルを通らないようにすること**です。不正な状態を表現不能にし、不正な操作を呼び出し不能にすることで、テストや実行時チェックを実行する前の段階で、極めて大きなクラスの欠陥を構造的に排除します。

## 証明責務としての型

型システムにおける型とは、取り得る値の集合です。型同士の関係性は、どの値と操作が許可されているかを規定します。コンパイラはプログラム全体にわたってその関係性を検証し、制約を満たせないコードを拒絶します。

プログラムが表現するモデルの範囲内において、型チェックの成功とは「コードが静的制約を満たしていることの機械的な証明」です。その証明の質は、モデル自体の厳密さに依存します。広すぎる型、無検証のアサーション、未検査の外部入力は、設計が想定していない値の混入を許し、証明の力を弱めてしまいます。

実行時の内部表現が似ていたとしてもドメイン概念を型レベルで厳密に区別し、状態遷移を型によって網羅的（Exhaustive）に扱うことが重要です。

## ロジックの前に設計を型で確定する

実装は、要件と不変条件を型システムへ翻訳することから始めます。これにより、複雑な処理コードを書く前に、考慮漏れの状態、曖昧な所有関係、不正な状態遷移が早期に浮き彫りになります。

エンジニアリングの本質的な仕事は、「正しい実装が自然に書け、設計に反する実装がコンパイルエラーとして拒絶されるモデル」を構築することです。そのモデルの上に実行時ロジックを記述することは、設計の最初の表現ではなく、モデルの具現化に過ぎません。

## テストとの関係分担

外部システムからの未検証入力や、アルゴリズム、統合境界、実行時のパフォーマンス特性など、コンパイラが静的に検証できない領域を検証するためにテストは依然として不可欠です。外部データは、信頼できるドメイン型として扱う前に実行時バリデーションを経なければなりません。

ただし、テストは弱すぎる型モデルの穴埋めとして使われるべきではありません。まず意図しないコードがコンパイルできないように型で設計を拘束し、その上で型だけでは証明できない振る舞いをテストします。
これは [唯一の事実源（Single Source of Truth）](single-source-of-truth.md) の原則に従います。静的に表現可能な不変条件については型モデルこそが権威ある表現であり、コンパイラがそのネイティブな強制・証明機構です。型システムが直接保証できることを、別個のテストコードで重複して検証する必要はありません。
