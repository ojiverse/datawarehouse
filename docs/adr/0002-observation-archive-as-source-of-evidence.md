# ADR-0002: Observation Archive を唯一の事実証跡（Source of Evidence）とする方針

* **ステータス**: 承認（Accepted）
* **決定日**: 2026-09-20
* **対象領域**: ドメイン設計 / データ整合性

## コンテキストと課題

本システムは、リアルタイム WebSocket 接続である **Discord Gateway** と、REST ベースの **Discord HTTP API** の 2 つの異なる経路からデータを収集する。

これら 2 つの経路から取得可能なデータには、本質的な「完全性（Completeness）」の差異が存在する。
* **Gateway イベント**: 投稿、編集、リアクション、削除など、発生したイベントの時系列生ログが得られる。
* **HTTP API レスポンス**: リクエスト時点で Discord 上に残存する最新の「状態（State）」のみが得られる。Gateway 停止中に投稿され即座に削除されたメッセージや、複数回編集された中間履歴は取得できない。

データパイプライン設計において、入力を共通イベントモデルへ強引に統一する目的から、HTTP API 取得メッセージを架空の Gateway イベント（`MESSAGE_CREATE` 等）へ捏造・変換するアンチパターンが存在する。これを許容した場合、実態として存在しなかったイベント履歴がデータ基盤に混入し、データの真正性と来歴（Provenance）が不可逆的に損なわれる。

## 検討した選択肢

### 選択肢 1: 全ての観測を共通の「イベント」として一元化
* **概要**: HTTP Backfill で取得したメッセージに対しても仮想的な `MESSAGE_CREATE` イベントを生成し、Gateway イベントと同一形式でアーカイブへ保存する。
* **メリット**: 後続の処理層が「イベント」のみを扱えばよいため、正規化ロジックが単純化される。
* **デメリット**: 取得経路の境界が失われ、「リアルタイムに観測された事実」と「事後的にスナップショットとして回収された事実」を識別不能となる。分析時に誤った中間状態の推測を誘発する。

### 選択肢 2: 取得経路の違いを来歴（Provenance）として保持し、生の事実証跡とする
* **概要**: Gateway 由来か HTTP 由来かをエンベロープ上で明確に区別し、Discord から受信した生のレスポンス構造を無加工で記録する。

## 決定事項

**選択肢 2 を採用する。**

* **架空のイベント捏造の禁止**: HTTP Backfill で取得されたデータを、未観測の Gateway イベントとして偽装・変換することを厳格に禁じる。
* **Observation の事実証跡化**: Observation Archive は、「Discord から何が観測されたか」を一切の解釈を挟まずに保存する唯一の事実証跡（Source of Evidence）とする。
* **厳格な来歴（Provenance）の付与**: すべての Observation に一意な ID、取得元種別（`gateway` / `http_backfill` / `http_reconciliation`）、観測タイムスタンプ、およびセッション/リクエスト識別子を付与することを義務付ける。

## 結果とトレードオフ

### メリット
* **データの信頼性と真正性**: 任意の分析結果に対し、「どのリクエスト/イベントで Discord から取得された事実に基づくのか」を客観的に証明可能。
* **将来の解釈変更への耐性**: 生データに不要な仮想解釈を混入させないため、事後的に正規化モデルの導出ロジックを変更する際の安全性が担保される。

### デメリットと対応策
* **後続パイプラインのロジック複雑化**: Canonical Store への正規化処理において、リアルタイムイベントと HTTP スナップショットの性質差を認識し、適切に競合解決・マージするロジックが必要となる。
  * *対応*: ドメイン設計の [processing/](../domain/processing/README.md) において、競合解決規則（Reconciliation Semantics）を独立した責務として明確に定義することで複雑性を制御する。
