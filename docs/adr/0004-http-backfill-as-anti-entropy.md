# ADR-0004: HTTP Backfill を定常的なアンチエントロピー機構とする方針

* **ステータス**: 承認（Accepted）
* **決定日**: 2026-09-20
* **対象領域**: ドメイン設計 / 運用アーキテクチャ

## コンテキストと課題

Discord のリアルタイムイベント受信（Gateway WebSocket）は、インターネットを介したストリーミング接続です。どれほど堅牢な接続管理を行っていたとしても、以下の事象による「潜在的な微小欠損（サイレントドロップ）」のリスクが常に存在します。

1. **予期せぬ切断時の境界損失**: 切断検知から再接続までの間に、Discord 側のセッションバッファからイベントが溢れ出た場合。
2. **インフラ側の一時的障害**: キューへの投入失敗、ワーカーのクラッシュ、ダウンストリームの一時的な遅延。
3. **長期運用に伴うエントロピー増大**: 数ヶ月〜数年のスパンで見ると、微細なイベント取りこぼしが蓄積し、全体のデータ整合性が静かに劣化する。

通常、HTTP Backfill は「システムの初期導入時」や「Gateway の大規模障害発生時」に運用者が手動で起動するエマージェンシーツールとして扱われがちです。しかし、人手による検知と運用に頼っている限り、潜在的なデータの虫食いを未然に防ぐことはできません。

## 検討した選択肢

### 選択肢 1: Backfill を障害時・手動運用の非常用ツールとする
* **概要**: 平常時は Gateway のみでデータを受信し、切断アラートが鳴った場合や初期導入時にのみ Backfill を手動・自動で起動する。
* **メリット**: Discord HTTP API のリクエスト消費を最小限に抑えられる。
* **デメリット**: Gateway が「正常に見えている」間に発生したサイレントな欠損を自己修復できず、長期的にデータ欠落が放置されるリスクが高い。

### 選択肢 2: Backfill を定常的なアンチエントロピー機構として位置づける
* **概要**: Backfill パイプラインを定常機能とし、Cron スケジューラによって直近数時間〜数日分のメッセージ履歴を HTTP 経由で定期巡回・照合させる。

## 決定事項

**選択肢 2 を採用する。HTTP Backfill を定常的なアンチエントロピー（Anti-Entropy）機構としてアーキテクチャに組み込む。**

* **結果整合性（Eventual Consistency）の担保**: Gateway が万一メッセージを取り逃していた場合でも、バックグラウンドの定期巡回によって「最終的には必ずデータが回収される」整合性保証を確立する。
* **パイプラインの統一**: 初回ロード、障害リカバリ、および定常照合のすべてで同一の Backfill クローラーエンジンを利用し、テスト頻度を高める。
* **レート制限との調和**: 定常巡回は低プライオリティのバックグラウンドタスクとして実行し、Discord API のレート制限を消費しすぎないインターバルで安全に回す。

## 結果とトレードオフ

### メリット
* **自己修復可能なデータ基盤**: 運用者が気付かない微小な通信障害やバグによる欠損が自動的に発見・補完され、データの信頼性が極めて高く保たれる。
* **運用の自動化**: 手動でのデータ照合やリストア作業の負担が劇的に削減される。

### デメリットと対応策
* **Discord API リクエスト数の増加**: 定期的に HTTP API を叩くため、Bot のレート制限枠を一部消費する。
  * *対応*: 巡回対象を「全チャンネルの全履歴」ではなく「直近 N 日間にアクティビティがあったチャンネル」に絞り込み、必要最小限のリクエスト数に抑える。
