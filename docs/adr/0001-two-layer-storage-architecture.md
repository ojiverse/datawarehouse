# ADR-0001: 2層ストレージアーキテクチャ（Observation Archive と Canonical Store）

* **ステータス**: 承認（Accepted）
* **決定日**: 2026-09-20
* **対象領域**: ドメイン設計 / アーキテクチャ設計

## コンテキストと課題

本システムは、Discord 上で発生する多種多様なイベントやメッセージを 5〜10 年という長期スパンで蓄積・分析することを目的としています。
この長期運用の過程において、以下の不可避な変化が発生することが予想されます。

1. **Discord API の進化**: 新規フィールドの追加、既存フィールドの非推奨化、イベント仕様の変更。
2. **分析要件とスキーマの進化**: DWH として抽出・集計したい属性や集計テーブル構造の後からの見直し。
3. **正規化・変換ロジックのバグ**: 初期実装時のパースミスや解釈の誤りが、後から判明するケース。

もし最初から単一の正規化データベース（例: PostgreSQL や D1 のテーブル）へ直接データを挿入・上書き更新する構造を採用した場合、元の生の JSON ペイロードが失われ、スキーマ変更時やバグ修正時に「過去数年分のデータを新しい変換規則で再計算する」ことが不可能になります。

## 検討した選択肢

### 選択肢 1: 単一の正規化リレーショナルデータベース
* **概要**: 受信したイベントを直ちにリレーショナルテーブルへ正規化して保存する。
* **メリット**: 設計がシンプルで、SQL による即時クエリが容易。
* **デメリット**: 生データが消失するためスキーマ変更やバグ修正時の再処理（Replay/Rebuild）が不可能。書き込み負荷がデータベースの接続数・性能に縛られる。

### 選択肢 2: 生ログのみを蓄積し、毎回オンデマンドで全件集計
* **概要**: オブジェクトストレージへ生ログを追記するのみとし、クエリ実行時に毎回全件をパースして集計する。
* **メリット**: 生データが完全に保護され、再計算の柔軟性が最も高い。
* **デメリット**: クエリを実行するたびに膨大な JSON ペイロードを全スキャン・パースする必要があり、クエリレイテンシと処理コストが実用的な許容範囲を超える。

### 選択肢 3: 生ログ（Observation Archive）と分析モデル（Canonical Store）の2層分離
* **概要**: 取得した生データを一切改変せずにオブジェクトストレージへ追記保存する層（Observation Archive）と、そこから抽出・正規化して分析用フォーマット（Apache Iceberg 等）でマテリアライズする層（Canonical Store）を明確に分離する。

## 決定事項

**選択肢 3（2層ストレージアーキテクチャ）を採用する。**

* **Observation Archive を第一級の市民とする**: 受信したペイロードは無加工の生データとして永続化し、システムにおける「唯一無二の事実証跡（Source of Evidence）」として扱う。
* **Canonical Store を派生表現とする**: Canonical Store のデータは、すべて Observation Archive からいつでも完全に再構築（Rebuild）可能であることを前提とする。
* **耐久性の優先順位**: Observation Archive への書き込み成功を最優先とし、Canonical 変換の遅延や失敗が生データ収集を阻害しないパイプラインを構築する。

## 結果とトレードオフ

### メリット
* **完全な再処理性**: スキーマ変更、正規化ルールの改善、またはデータ破損が発生しても、過去全期間の生ログをリプレイして Canonical Store をゼロから無停止で再生成できる。
* **障害の局所化**: 変換処理やクエリ層に障害が発生しても、生データの収集・永続化パスは影響を受けずに稼働し続ける。
* **長期運用の担保**: 5〜10年後に分析基盤の技術スタックを全面刷新する場合でも、生データアーカイブさえあれば移行が容易に行える。

### デメリットと対応策
* **ストレージ容量の二重化**: 生ログと正規化データの双方が保存されるため、保存容量が増加する。
  * *対応*: Cloudflare R2 のストレージ料金（$0.015/GB/月）は極めて低廉であり、数ギルド〜数十ギルドのテキストデータ規模であれば月額数十円〜数百円の範囲に収まるため、再処理性のメリットがコストを大幅に上回ると判断した。
