# ADR-0006: Discord Gateway のセッション管理に Durable Objects を採用する方針

* **ステータス**: 一部置換（Partially Superseded by ADR-0007）
* **決定日**: 2026-09-20
* **対象領域**: アーキテクチャ設計 / インフラストラクチャ設計

## コンテキストと課題

Discord のリアルタイムイベントを受信するには、Discord Gateway に対して長時間の **WebSocket 接続** を維持する必要がある。
この接続管理には、以下のプロトコル制約が伴う。

1. **排他的な単一接続**: 同一シャードに対して複数クライアントが同時に `Identify` した場合、セッションが切断・無効化される。
2. **シーケンス番号の厳密な追跡**: 切断時にイベントを取りこぼさず再開（`Resume`）するためには、受信したイベントの `sequence` 番号を正確にメモリまたはストレージで保持し続ける必要がある。
3. **ハートビートの定常送信**: 約 41 秒間隔でハートビートを定期送信し、死活監視を行わなければ Discord 側から切断される。

通常、サーバーレス環境（Stateless Workers）は短命なリクエスト処理を前提としており、長時間の WebSocket 接続やインメモリ状態の維持が困難である。このため、Gateway 接続のためだけに外部の常駐サーバー（Fly.io や ECS 等）を併用する構成が一般的であった。

## 検討した選択肢

### 選択肢 1: 外部の常駐コンテナ環境（Fly.io / Railway / ECS）を併用
* **概要**: Gateway クライアントのみを常駐コンテナで動かし、受信イベントを Webhook やキュー経由で Cloudflare へ送信する。
* **メリット**: 通常の Node.js / Go 製 Discord ライブラリがそのまま利用可能であり、長時間の WebSocket 維持が容易。
* **デメリット**: 複数サービスの管理工数が発生し、月額固定費も追加で発生する。

### 選択肢 2: Cloudflare Durable Objects（DO）を採用
* **概要**: 単一シャードの Gateway セッション管理を 1 つの Durable Object インスタンスへ委譲し、WebSocket 接続の排他的所有、インメモリ状態維持、および Alarm API によるハートビート自律送信を行う。

## 決定事項

**選択肢 2 を採用する。Discord Gateway の接続管理に Cloudflare Durable Objects を採用する。**

* **単一所有権の確立**: 1 シャードにつき 1 つの DO インスタンス（`shard:0`）をマッピングし、排他的に WebSocket を接続・管理する。
* **自律的なタイマー管理**: DO の Alarm API を利用し、外部スケジューラに頼らずインスタンス自身が自律的にハートビートを送信・監視する。
* **Workers Paid の枠内運用**: 1 インスタンスの常時稼働であれば、Workers Paid プランに含まれる Duration 枠（400,000 GB-s）内に収まり、追加費用なしで常時接続が実現可能。

## 結果とトレードオフ

### メリット
* **基盤の Cloudflare 一本化**: 外部コンテナを契約・保守する必要がなく、インフラ構成・デプロイパイプライン・監視が一元化される。
* **Resume の高親和性**: DO トランザクションストレージに `session_id` と `sequence` をアトミックに書き込めるため、再起動時の Resume 復帰が高速。

### デメリットと対応策
* **コード更新時のインスタンス再生成**: デプロイ時に WebSocket 切断が一時的に発生する。
  * *対応*: 切断前にセッション情報をストレージへフラッシュし、新インスタンス起動直後に `Resume` を実行することで、イベント欠損ゼロでのシームレスな移行を実現する。
