# ADR-0001: 2層ストレージアーキテクチャ（Observation Archive と Canonical Store）

* **ステータス**: 承認（Accepted）
* **決定日**: 2026-09-20
* **対象領域**: ドメイン設計 / アーキテクチャ設計

## コンテキストと課題

本システムは、Discord 上で発生する多種多様なイベントおよびメッセージを 5〜10 年の長期スパンで蓄積・分析することを目的とする。
この長期運用の過程において、以下の不可避な変化の発生が予想される。

1. **Discord API の進化**: 新規フィールドの追加、既存フィールドの非推奨化、イベント仕様の変更。
2. **分析要件とスキーマの進化**: DWH として抽出・集計対象とする属性や集計テーブル構造の見直し。
3. **正規化・変換ロジックの不具合**: 初期実装時のパースミスや解釈の誤謬の発覚。

初期段階から単一の正規化データベース（PostgreSQL や D1 等）へ直接データを挿入・上書き更新する構造を採用した場合、元の生の JSON ペイロードが不可逆的に失われ、スキーマ変更時や不具合修正時に過去データを新規則で再計算することが不可能となる。

## 検討した選択肢

### 選択肢 1: 単一の正規化リレーショナルデータベース
* **概要**: 受信イベントを直ちにリレーショナルテーブルへ正規化して保存する。
* **メリット**: 設計が単純であり、SQL による即時クエリが容易。
* **デメリット**: 生データが消失するためスキーマ変更やバグ修正時の再処理（Replay/Rebuild）が不可能。書き込み負荷がデータベースの接続数および処理能力に制約される。

### 選択肢 2: 生ログのみを蓄積し、オンデマンドで全件集計
* **概要**: オブジェクトストレージへ生ログを追記保存するのみとし、クエリ実行時に毎回全件をパースして集計する。
* **メリット**: 生データが完全に保持され、再計算の柔軟性が最も高い。
* **デメリット**: クエリ実行ごとに膨大な JSON ペイロードの全スキャン・パースを要し、クエリレイテンシと処理コストが許容範囲を超過する。

### 選択肢 3: 生ログ（Observation Archive）と分析モデル（Canonical Store）の2層分離
* **概要**: 取得生データを改変せずにオブジェクトストレージへ追記保存する層（Observation Archive）と、そこから正規化して分析用フォーマット（Apache Iceberg 等）でマテリアライズする層（Canonical Store）を明確に分離する。

## 決定事項

**選択肢 3（2層ストレージアーキテクチャ）を採用する。**

* **Observation Archive の第一級市民化**: 受信ペイロードは無加工の生データとして永続化し、システムにおける「唯一無二の事実証跡（Source of Evidence）」として位置づける。
* **Canonical Store の派生表現化**: Canonical Store のデータは、すべて Observation Archive からいつでも完全に再構築（Rebuild）可能であることを前提とする。
* **耐久性の優先順位**: Observation Archive への書き込み成功を最優先とし、Canonical 変換の遅延や失敗が生データ収集を阻害しないパイプラインを確立する。

## 結果とトレードオフ

### メリット
* **完全な再処理性**: スキーマ変更、正規化ルールの改善、またはデータ破損が発生した場合であっても、過去全期間の生ログをリプレイして Canonical Store をゼロから無停止で再生成可能。
* **障害の局所化**: 変換処理やクエリ層に障害が発生しても、生データの収集・永続化パスは影響を受けずに稼働を継続。
* **長期運用の担保**: 将来的に分析基盤の技術スタックを刷新する場合であっても、生データアーカイブを事実源として安全に移行可能。

### デメリットと対応策
* **ストレージ容量の二重化**: 生ログと正規化データの双方が保存されるため、保存容量が増加する。
  * *対応*: Cloudflare R2 のストレージ料金（$0.015/GB/月）は低廉であり、数ギルド〜数十ギルドのテキストデータ規模であれば費用増加は極めて軽微である。再処理性の獲得がコスト要因を大幅に上回ると判断した。
