# ADR-0003: コア DWH においてリレーショナル DB（D1 等）を必須としない方針

* **ステータス**: 一部置換（Partially Superseded by ADR-0010）
* **決定日**: 2026-09-20
* **対象領域**: アーキテクチャ設計 / インフラストラクチャ設計

> **置換注記**: コア DWH に D1 等を必須としない判断は維持する。Backfill cursor を Queue message のみに保持する決定は ADR-0010 により置換された。

## コンテキストと課題

Cloudflare 上でアプリケーションを構築する際、リレーショナルデータベースとして **Cloudflare D1** が提供されている。
クローラーの進行状態管理や受信データの保存先として、直感的に D1 の導入が検討されやすい。

しかし、データウェアハウス（DWH）の中核データパスにリレーショナル DB を組み込む場合、以下の制約とリスクが生じる。

1. **書き込み性能とクォータの限界**: D1 にはデータベースサイズの上限（現行数GB〜数十GB）や、書き込みスループット（1秒あたりのトランザクション数）の制約が存在する。
2. **ストレージコストの増大**: オブジェクトストレージ（R2）に比べ、マネージド RDB の保存コストは数倍〜数十倍高価となる。
3. **運用の結合度**: RDB のマイグレーションやスキーマロックが、リアルタイム取り込み処理の可用性を脅かす単一障害点（SPOF）となりやすい。

## 検討した選択肢

### 選択肢 1: 状態管理および正規化データ保存に Cloudflare D1 を採用
* **概要**: Backfill の進行カーソルや、最新のメッセージ・チャンネル状態を D1 のテーブルで管理する。
* **メリット**: SQL による手軽な CRUD 操作と、即時のポイントルックアップが可能。
* **デメリット**: データ量増加に伴う容量制限の圧迫、書き込みレートの飽和、および将来的なテーブル肥大化に伴うコスト・移行負担が大きい。

### 選択肢 2: D1 を必須とせず、Queue の連鎖とオブジェクトストレージ（R2 + Iceberg）のみで完結
* **概要**: Backfill のカーソルは Cloudflare Queues のメッセージペイロード内で自己連鎖させ、永続化ストレージは R2 上のファイル（Observation）とオープンテーブルフォーマット（Apache Iceberg）のみで構成する。

## 決定事項

**選択肢 2 を採用する。コア DWH のデータパスにおいて D1 等の RDB を必須としない。**

* **ステートレスな Backfill 実行**: クローラーの進行状態はキューのメッセージ自体（`channel_id`, `before_id`）に保持させ、データベースへの書き込みなしに非同期連鎖で完走させる。
* **ストレージのオブジェクトストレージ統一**: 生データ（Observation）も正規化データ（Canonical）もすべて R2 上に集約し、スケーラビリティのボトルネックを排除する。
* **D1 の位置づけ**: D1 を完全排除するのではなく、将来的に管理 UI のメタデータ管理など、明確な必要性が確認された補助機能に限定し、コア DWH パイプラインからは独立させる。

## 結果とトレードオフ

### メリット
* **高スケーラビリティ**: 容量制限に制約されることなく、数千万件以上のメッセージを低コストで永続化可能。
* **運用負荷の極小化**: データベースのコネクション管理、マイグレーションロック、バックアップ・リストア運用が不要となる。

### デメリットと対応策
* **単一メッセージの即時検索（Point Query）の制約**: R2 SQL や Iceberg は大規模な集計・スキャンクエリに最適化されているため、特定 1 メッセージをミリ秒単位で検索する用途には適さない。
  * *対応*: 本システムは DWH（分析基盤）であり、OLTP 的な高速単件取得は主目的ではない。将来的に必要となった場合は、分析基盤とは別に特定のインデックスキャッシュや検索エンジンを前段に配置して対処する。
