# ADR-0005: 主要プラットフォームとして Cloudflare を採用する方針

* **ステータス**: 承認（Accepted）
* **決定日**: 2026-09-20
* **対象領域**: 全体アーキテクチャ / 技術選定

## コンテキストと課題

本プロジェクトは、個人または小規模組織において、5〜10 年の長期にわたり運用を継続可能な Discord DWH の構築を目的とする。
インフラ基盤の選定において、以下の制約を満たす必要がある。

1. **経済的持続性（低コスト運用）**: 月額数千円〜数万円規模の固定費が発生する構成は、長期運用の持続可能性を損なうため許容されない。
2. **保守工数の極小化（サーバーレス）**: OS パッチ適用、クラスタ管理、DB バージョンアップ等の定常運用工数を排除する。
3. **転送量課金（エグレス課金）の回避**: 数千万件規模のログを蓄積・分析する際、データのエグレス課金がコストリスクとなる。

## 検討した選択肢

### 選択肢 1: AWS（ECS + S3 + Athena）
* **メリット**: エンタープライズ標準の完成度、豊富な実績とエコシステム。
* **デメリット**: 常駐コンテナ（Fargate）の基本料金、NAT Gateway 費用、S3 のデータ転送量課金およびリクエスト課金が重なり、最低でも月額数千円〜1万円以上の固定費が発生しやすい。

### 選択肢 2: 自宅サーバーまたは VPS（Docker / MinIO / ClickHouse）
* **メリット**: ハードウェア費用のみで済み、自由度が高い。
* **デメリット**: ハードウェア故障、停電、回線切断、OS 保守などの運用工数が高く、5〜10年の継続性に重大な懸念が残る。

### 選択肢 3: Cloudflare（Workers + Durable Objects + Queues + R2）
* **メリット**: 
  * **エグレス課金ゼロ**: R2 からのデータ転送量課金が一切発生しない。
  * **低額な定額枠**: Workers Paid（月額 $5〜）で、常時稼働の Durable Objects と 10GB 以上の R2 ストレージが利用枠内に収まる。
  * **高い統合性**: WebSocket 常時接続（DO）、非同期キュー（Queues）、オブジェクトストレージ（R2）、および分散 SQL（R2 SQL）が単一プラットフォームで完結する。

## 決定事項

**選択肢 3（Cloudflare）を主要インフラ基盤として採用する。**

* **経済的持続可能性の最大化**: ミニマムコストで、高耐久なデータウェアハウス基盤を成立させる。
* **抽象度の分離によるロックイン緩和**: ドメイン設計から Cloudflare 固有の語彙を徹底排除し、将来のプラットフォーム移行やハイブリッド展開を阻害しない設計規律を維持する。

## 結果とトレードオフ

### メリット
* 運用維持コストが極めて低く、長期にわたり無理なく運用を継続可能。
* データ蓄積量や分析頻度が増加しても、転送量課金の懸念がない。

### デメリットと対応策
* **プラットフォーム固有の制約**: Workers の CPU 実行時間制限や、新データ機能（R2 SQL, Pipelines）の発展途上な側面が存在する。
  * *対応*: バッチ集約（Queues）やステートレス連鎖を活用して時間制限を回避するとともに、オープンなテーブルフォーマット（Apache Iceberg）を採用してデータのポータビリティを確保する。
