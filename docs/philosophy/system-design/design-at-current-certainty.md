# 現在の確実性のレベルで設計する（Design at the Current Level of Certainty）

設計は、**確定済みの既知事実に対して厳格（Strict）であり、未確定の未知事項に対して寛容（Permissive）**でなければならない。設計の目的は、将来の要件を先回りして過剰に予測することではない。現時点で立証された意味と制約を確実に保護しつつ、具体化されていない将来要件のために意図的な「余白」を確保することにある。

これは、新規データソースやドメインを追加する初期フェーズにおいて特に重要となる。分類体系、派生状態、検索インデックス、キャッシュ構造、ライフサイクルモデルなどの将来像を早期に設計へ焼き込む行為は、単なる仮説を硬直した制約へと固定化させる弊害を伴う。

したがって、設計上の核心的命題は「将来どうなり得るか」ではなく、**「判明している事実に照らし、何を損失または矛盾させてはならないか」**である。

## 生き残るべき事実の優先

システムが永続化すべき振る舞いおよび意味から演繹し、それを保護する最小限の不変条件を導出する。例えば、データソースがある時間的意味を持つ事実を報告している場合、長期的に保護すべき設計関心事は「その意味論が解釈過程で失われないこと」である。初期段階で特定のテーブルレイアウトや抽象型を直ちに決定する必要はない。

意味的な差異は、その表現形式（ストレージ構造や型）よりもはるかに安定している。2つのデータが等価として扱えないことが明白であっても、それらを別個のテーブルに分離すべきか、異なるバリデーションルールで扱うべきかは、要件が深化するまで決定を保留できる。まず意味の区別を確定させ、表現形式の固定化は要件が正当化するまで遅延させる。

所有権の境界設定も同様である。プロバイダ固有の生データがドメインの正（Truth）を汚染してはならない場合、生データとドメイン解釈の間に厳格な境界を引く。その境界が要求する以上の汎用フレームワークを早期に導入してはならない。優れた抽象化とは「複数の実例によって証明された共通の不変条件」を表現するものであり、将来のユースケース間の表面的な類似性は抽象化の根拠とならない。

## 不確実性の設計情報としての扱い

設計過程における未解決の疑問は、設計の不備を必ずしも意味しない。多くの場合、「システムが責任を持って決定を下すための十分な要件をまだ持ち合わせていない」事実を示している。

既知の不変条件を維持するために即時決定を要しない事柄は、後の段階で情報を損失せず、かつ既存契約を破壊せずに決定可能である限り、**意図して決定を未確定のまま保留（Open）**とする。ストレージレイアウト、保持期間、リビジョン管理戦略、派生モデルなどは、初期設計において本カテゴリに該当する典型例である。

これは契約の曖昧な放置を意味しない。既知の不変条件は型やドメイン定義を用いて厳密に表現する。重要なのは「精度」と「推測」の峻別である。**確定済みの意味論の破壊を困難にする一方で、未確認の分類体系を変更困難にしてはならない。**

判断の取り扱いは以下の基準に従う。

* **確定済みの意味および制約**: 明示的かつ恒久的に固定する。
* **想定される将来要件**: 受容可能な余白を確保する。
* **代替可能な実装選択**: ドメイン契約の外部へ隔離する。

決定の永続性が高いほど、その決定を正当化するための証拠基準を厳格化しなければならない。局所的な実装詳細は安価に変更可能であるが、ドメイン概念や公開契約を後から改変することは極めて高いコストを要する。

## 議論の経過と設計の形状の峻別

設計文書は、設計議論の経過を書き起こした議事録ではない。設計者が多数の代替案を比較検討したとしても、読者はその検討履歴を知る必要はなく、現在の論理的結論を把握できれば足りる。

特定の概念が存在しないことを明記するためだけに、未採用の概念を本文へ持ち込むことを禁じる。不要な概念の導入は読者の認知負荷を増大させるためである。否定的な決定を記録すべき対象は、「周辺アーキテクチャから見て、一般的な読者が当然その設計を採用すると類推する場合」や、「不在そのものが重要な責務境界を保護している場合」に限定される。

文書は、読者が理解するために必要な論理順序で整理されるべきであり、設計チームが発見した時系列順で構成してはならない。読者は、過去の議論の紆余曲折を経ることなく、「なぜその境界が存在するのか」を客観的に導出可能でなければならない。

## 早期の解釈より情報の保存を優先

将来要件が不確実な段階においては、早期に過度な正規化へコミットするよりも、**元情報の意味と来歴（Provenance）を忠実に保存すること**を最優先とする。保存された生データは後から任意に再解釈・再計算可能であるが、初期の安易な正規化によって削ぎ落とされた情報は復元不可能となるためである。

計算結果の扱いも同様である。ある結果がドメインの事実から算出されたものである場合、利便性のみを理由としてその計算結果を「第2の事実源」に格上げしてはならない。計算処理は、入力の本来の意味を抹消したり、それと競合したりしてはならないという不変条件を遵守する。

## 既知条件充足による設計完了

設計は、**「すべての確定した要件に明確な不変条件と所有者が割り当てられ、利用側が小さく安定した契約に依存でき、未解決の疑問が情報の損失や矛盾を引き起こすことなく安全に保留されている状態」**に達した時点で完了とみなす。

その完了点を超えて過剰な詳細を詰め込む行為は、設計品質を向上させるどころか、かえって低下させる。過剰な概念定義は、将来の保守者が遵守または撤回を迫られる不要な語彙、依存関係、および暗黙の制約を増大させるためである。

設計は、**要件 → 不変条件 → 権威ある所有者 → 最小限の安定した境界 → 観測可能な振る舞い**という最短の論理連鎖で説明可能な状態を維持する。

将来新たな要件が判明した際は、その証拠に基づいて同様の思考プロセスを再適用する。初期設計を固定化された予言として扱ってはならない。優れた設計とは、**「その時点で真実であったことに対して精密であり、それ以外のすべてを意図して再考可能な状態に保った設計」**である。
