# コメントは「Why」を記録する（Comments Explain Why）

ソースコード内のコメントは、リポジトリにおいて最も保守が難しい情報形態の1つです。コメントは非構造化された自然言語であり、コンパイラによる検証が効かず、リファクタリングツールで自動追従することもできません。実装が変化するにつれてコメントは容易に陳腐化し、誤解を招くノイズになります。

したがって、すべてのコメントは保守負債を生むものとして扱います。コメントは極力少なく抑え、型、命名、プログラム構造、テストコード、あるいは設定ファイルでは明確に表現できない「本質的な設計・実装の意図」のためにのみ使います。

## 責務の明確な分担

| 表現手段 | 担う責務 | 答えるべき問い |
| :--- | :--- | :--- |
| **Docstring（仕様定義）** | 呼び出し側に公開される外部契約 | この抽象は何を提供するのか？（What） |
| **実装コード（Implementation）** | 実行される具体的な仕組み・手続き | どのように実現しているのか？（How） |
| **コメント（Comment）** | コード自体からは復元できない判断理由 | **なぜこの選択が必要だったのか？（Why）** |

Docstring は関数の本体を解説する場所ではなく、契約を記述する場所です。実装コードは、明確な命名、適切な型、境界分離、および制御フローによって、それ自体で「How」を雄弁に語るべきです。そしてコメントは、複数の現実的な選択肢の中から「なぜそれを選んだのか」という意思決定の根拠を保存するためにのみ存在します。

## コメントが記録すべきこと

価値のあるコメントとは、以下のようなコンテキストを保存するものです。

* 非自明な実装を余儀なくさせた、外部システムやライブラリの制約
* 一見するとよりシンプルで自然に見える代替案が、採用できなかった理由
* コードの表面には現れない、トレードオフや性能上の制約
* そのコードを変更・削除すると、どの不変条件が破壊されてしまうのかという警告

コメントは、将来の保守者が「この前提制約が今も適用されるか」を評価できるだけの論理を含むべきであり、単に使われている技術にラベルを貼るだけのものであってはなりません。

## コメントで補おうとしてはならないこと

コードの動作説明、型の言い直し、制御フローの実況中継、あるいは読みにくい実装の言い訳としてコメントを使ってはなりません。コードが何を意図しているかが伝わらないのであれば、まずデータモデル、変数名、関数分割、あるいは実装そのものを改善すべきです。
