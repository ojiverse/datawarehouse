# 正しさを判定する評価基準を最初に築く（Optimize Function First）

システム開発において最も価値のある構造的な資産は、**「自分の行った変更が正しかったのかどうかを、即座に知ることができる素早い検証の循環」**です。

しかし、検証の循環を高速に回すためには、その良し悪しを機械的・客観的に測定するための**「評価の基準（客観的な判定器）」**が欠かせません。何をもって成功とし、何をもって後退とするのかの判定基準を持たないまま作業を進めると、どれほど素早く変更を重ねたとしても、それは目隠しをしてサイコロを振るような迷走（当てずっぽうの試行錯誤）に終わってしまいます。

## 実装に飛びつく前に、成否の判定器を用意する

新しい機能や改修に着手する際、もっとも価値の高い作業は、実装コードを書き始めることではなく、**「望ましい結果が得られたことを客観的に証明する判定器」を先に築くこと**です。

この判定器が存在していれば、あらゆる変更が前進であるか改悪であるかを、人間の主観や曖昧な勘に頼ることなく、数秒で明確に判定できます。

課題の性質に応じて、判定器は以下のような形で準備します。

* **データ処理や正規化ロジック**: 代表的な入力ペイロードと、そこから抽出されるべき期待結果をまとめた評価用のデータセットを先に揃える。
* **状態遷移や不変条件の保護**: 不正な遷移や想定外のデータが混入した際に即座に不合格を出す、性質に基づいた検証テスト（不変条件の網羅的チェック）を用意する。
* **通信や外部連携の処理**: 実際に外部とのやり取りをシミュレートし、通信ログと保存結果を検証できる再現手順やスクリプトを先に確立する。
* **アーキテクチャの変更**: 静的な型定義を厳密に固め、設計に反するコードがコンパイルの段階で機械的に弾かれる状態を先に作る。

## 機械に実装を委ねる時代における絶対的な支柱

生成 AI や自動化エージェントを活用して実装を進める現代の開発において、この「評価基準の先行」は成否を分ける決定的な鍵となります。

客観的な判定基準が存在しない状態で機械にコードを書かせると、何千行ものそれらしいコードが生成され、人間はその正しさを確かめるために膨大な時間を費やして行ごとの解読を強いられます。
しかし、明確な判定器があらかじめ用意されていれば、機械はその判定器に合格するまで自律的に修正を繰り返すことができ、人間は「判定器をすべて通過したという客観的な証拠」を確認するだけで、安心してその成果を受け取ることができます。

**「評価基準を先に築き、その上で最小限の実装を流し込む」**という順序を徹底することで、無駄な手戻りを排除し、確信を持って開発を前進させることができます。
