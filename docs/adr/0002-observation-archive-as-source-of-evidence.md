# ADR-0002: Observation Archive を唯一の事実証跡（Source of Evidence）とする方針

* **ステータス**: 承認（Accepted）
* **決定日**: 2026-09-20
* **対象領域**: ドメイン設計 / データ整合性

## コンテキストと課題

本システムは、リアルタイムな WebSocket 接続である **Discord Gateway** と、REST ベースの **Discord HTTP API** の 2 つの異なる経路からデータを収集します。

これら 2 つの経路から取得できるデータには、本質的な「完全性（Completeness）」の差が存在します。
* **Gateway イベント**: 投稿、編集、リアクション、削除など、発生したイベントの時系列の生ログが得られる。
* **HTTP API レスポンス**: リクエスト時点で Discord 上に残っている最新の「状態（State）」のみが得られる。Gateway 停止中に投稿され即座に削除されたメッセージや、複数回編集された中間履歴は取得できない。

データパイプラインを設計するにあたり、「すべての入力を共通のイベントモデルに統一したい」という誘惑から、HTTP API で取得したメッセージを架空の Gateway イベント（例: `MESSAGE_CREATE`）として捏造・変換してしまうアンチパターンが存在します。これを許容すると、実態としては存在しなかったイベント履歴がデータ基盤に混入し、データの真正性と来歴（Provenance）が恒久的に損なわれます。

## 検討した選択肢

### 選択肢 1: 全ての観測を共通の「イベント」として一元化する
* **概要**: HTTP Backfill で取得したメッセージに対しても仮想的な `MESSAGE_CREATE` イベントを生成し、Gateway イベントと全く同一の形式としてアーカイブへ保存する。
* **メリット**: 後続の処理層が「イベント」のみを扱えばよいため、正規化ロジックが単純になる。
* **デメリット**: 取得経路の境界が失われ、「実際にリアルタイムで観測された事実」と「後からスナップショットとして回収した事実」を区別できなくなる。分析時に誤った中間状態の推測を生む原因となる。

### 選択肢 2: 取得経路の違いを来歴（Provenance）として保持し、生の事実の証跡とする
* **概要**: Gateway 由来か HTTP 由来かをエンベロープ上で明確に区別し、Discord から受け取った生のレスポンス構造をそのまま無加工で記録する。

## 決定事項

**選択肢 2 を採用する。**

* **架空のイベント捏造の禁止**: HTTP Backfill で得られたデータを、観測していない Gateway イベントとして偽装することを厳格に禁じる。
* **Observation を「事実の証跡」と定義**: Observation Archive は、「Discord から何が観測されたか」を一切の解釈を挟まずに保存する source of evidence とする。
* **厳格な来歴（Provenance）の付与**: すべての Observation に一意な ID、取得元種別（`gateway` / `http_backfill` / `http_reconciliation`）、観測タイムスタンプ、およびセッション/リクエスト識別子を必ず付与する。

## 結果とトレードオフ

### メリット
* **データの信頼性と真正性**: どのような分析結果に対しても、「それはどのリクエスト/イベントで Discord から取得された事実に基づくのか」を正確に説明できる。
* **将来の解釈変更への耐性**: 生データに不要な仮想解釈を混ぜないため、後から正規化モデルの導出ロジックを変更する際の安全性が担保される。

### デメリットと対応策
* **後続パイプラインのロジック複雑化**: Canonical Store への正規化処理において、リアルタイムイベントと HTTP スナップショットの性質差を認識し、適切に競合解決・マージするロジックが必要になる。
  * *対応*: ドメイン設計の [processing/](../domain/processing/README.md) において、競合解決規則（Reconciliation Semantics）を独立した責務として明確に定義することで複雑性を制御する。
